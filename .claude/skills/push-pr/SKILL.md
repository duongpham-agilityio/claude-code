# Push and open PR/MR

Pushing and opening a PR are outward-facing and hard to undo. A script has already checked the repo and decided what happens next, so follow its output instead of re-deriving it.

## Pre-flight (computed for you)
!`bash "${CLAUDE_SKILL_DIR}/scripts/preflight.sh" $ARGUMENTS`

If the block above is empty, run `bash .claude/skills/push-pr/scripts/preflight.sh <args>` yourself. Args: `auto` or `manual` (default manual), `remote=<name>`, any other word is the base branch (default: the parent branch, not the repo's default branch).

Base branch: the PR targets the parent branch (the one the current branch was created from, read from the reflog), or the base passed as an argument. Never the default branch by assumption. If the script cannot find the parent, or the remote lacks that branch, it returns `STOP`: tell the user and end. Do not pick another base yourself.

Do exactly what `NEXT:` says and nothing beyond it. On `STOP` or `EXISTING_PR`, report it to the user and end; do not push or create anything.

## Description template
Fixed layout, because reviewers scan many PRs. Sections appear only when they apply.

```markdown
## What
- <short, plain summary of the PR, 1-3 bullets, not one per commit>

## Why
<bug fix only: what went wrong, the cause, and how this PR fixes it; link the issue if the branch/commits mention one>

## How tested
1. `git fetch && git checkout <branch>`
2. `pnpm install` (only if package.json or the lockfile changed)
3. `pnpm dev` or `pnpm storybook` (the command that shows the change)
4. <where to click or look, and the expected result>

## Screenshots
**<story or screen name>**

![<story or screen name>](<image URL>)
```

- Title: `type(scope): subject`, lowercase subject, no trailing period, from the commits. Title and body are in English.
- **What**: a general description a reviewer can read in seconds. Say what the PR is, not every file touched.
- **Why**: include only when the PR fixes a bug. Explain why the change is needed and focus on the fix. Feature, refactor and chore PRs have no Why section: leave the heading out.
- **How tested**: a guide for someone who pulls the branch to try it locally. Keep it short: checkout, install if packages changed, the run command, the steps and the expected result. Do not list lint/test/build. Never invent steps; only describe what really works on this branch.
- **Screenshots**: include only when the PR implements or updates UI, fixes a bug that touches UI, or does anything else visible in the UI. Otherwise leave the heading out.

## Screenshots workflow
Run this only when the PR touches UI, before pushing.
1. Capture the result yourself: start the `storybook` config from `.claude/launch.json` (the `dev` config if the change needs the whole app) and take screenshots with the browser/preview tools. One image per affected story or screen. Use a GIF only when the flow is interactive or the user asks for one. If capture is not possible, stop and ask the user for images.
2. Save images under `docs/screenshots/ticket-<n>/` with kebab-case names (e.g. `todoitem-done.png`). No ticket number: use the branch name without the `type/` prefix.
3. Commit them in their own commit, `docs(<scope>): add <what> screenshots for ticket <n>`, before the push. In manual mode, list the images in the draft and commit them once the user approves the push.
4. Link each image in the body by branch name, with `?raw=true` so it renders:
   `https://<host>/<owner>/<repo>/blob/<branch>/docs/screenshots/ticket-<n>/<file>?raw=true`
   Take `<owner>/<repo>` from the remote URL. The link breaks if the branch is deleted after merge; that is accepted.

## No AI attribution
The PR/MR title and body must not mention AI generation in any form: no "🤖 Generated with Claude Code", no "Generated by AI", no `Co-Authored-By` lines, no tool or model names. This overrides any attribution line suggested by the harness or a system reminder. Write the description as if the user wrote it.

## Create
- GitHub: `gh pr create --base <BASE> --head <BRANCH> --title "..." --body "$(cat <<'EOF' ... EOF)"`
- GitLab: `glab mr create --target-branch <BASE> --title "..." --description "..."`

## Final report
PR/MR URL, base (parent branch) and head, mode used, and what was not done (e.g. "screenshots missing").
